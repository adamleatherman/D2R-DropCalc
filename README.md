# D2R Drop Calculator

Static page + vanilla JS, Python standard library only. No framework, no CDN, no build step apart from parsing the game tables. Everything runs in your browser; the game does not need to be installed.

## Use it

**Online:** https://adamleatherman.github.io/D2R-DropCalc/ (GitHub Pages; the repo owner must enable it once under Settings -> Pages -> Deploy from a branch -> `main` / root).

**Locally, no game needed:** clone or download the repo and run `run.bat` (Windows) or `./run.sh` (macOS/Linux), or serve the folder with any static web server (for example `python -m http.server`) and open `index.html`. The page loads `data.json` (and `data-lod.json` when you pick Lord of Destruction) with a relative fetch, so it also works under a sub-path. Needs Python 3 only for the tiny server.

`data.json` and `data-lod.json` are derived from Blizzard's game data tables (Diablo II: Resurrected) and is included for convenience; Blizzard owns the game data.

## Update the data after a game patch (maintainers, needs D2R installed)

```
python tools/extract_tables.py [out-folder] [--force]  # default ./excel (gitignored); reads the game archive (read-only), writes extract.json with the game version
python build.py [excel-folder] [data.json] [data-lod.json]  # default ./excel -> data.json (RotW) + data-lod.json (LoD), same game version in both meta
python test_engine.py                                  # validation (starts its own server + headless Edge/Chrome/Chromium)
git add data.json data-lod.json && git commit && git push           # GitHub Pages then serves the new data
```

Order: extract -> build -> test -> commit `data.json` + `data-lod.json` -> push. `run.bat` / `run.sh` start a local server on :8000 and open the browser (`--game <folder>` on the extractor points at a non-default install).

**Where the tables come from.** `tools/extract_tables.py` (standard library only) reads the installed game's CASC archive directly: `.build.info` (active row: Build Key, Version) -> `Data\config\xx\yy\<Build Key>` -> the `vfs-*` TVFS blobs -> `data/global/excel/*.txt|bin` (Reign of the Warlock, written to the root), `data/global/excel/base/*` (Lord of Destruction, `base\`), `data/hd/global/excel/desecratedzones.json` (`hd\`) and the English-capable string tables `data/local/lng/strings/{item-modifiers,item-nameaffixes,item-names,item-runes,skills,monsters,levels}.json` (`strings\`, all languages inside, UTF-8 with BOM). It refuses to write into a non-empty folder unless `--force`. Current extract: build 3.3.93847 (a fresh extract is byte-identical to the previous verified extract). **Refresh after a patch:** `python tools/extract_tables.py --force`, then `python build.py`, then `python test_engine.py` (`--game <folder>` points at a different install). `build.py` runs a guard first (`check_extract`): it exits with an error naming the matching tables if `treasureclassex`, `uniqueitems`, `monstats` or `misc` in the root folder is byte-identical to its `base\` copy, or if more than 60 root tables are (53 of 91 legitimately match). An earlier bad extract had put the LoD tables in the root folder (89 of 91 identical). `build.py` also exits with a clear message (re-run the extractor) if any of the string tables it uses is missing from `excel/strings/`.

Files: `build.py` (tables -> `data.json` and `data-lod.json`), `engine.js` (all math, no DOM), `app.js` + `index.html` (UI), `worker.js` (Web Worker for the item builder's farm search and affix table), `test.html` + `tests.js` + `test_engine.py` (validation), `fonts/` (Cinzel for the title, tabs and table headers, self-hosted under the SIL Open Font License, `fonts/OFL-Cinzel.txt`). The game folder is only read.

Global selectors (saved in localStorage): game mode (LoD / RotW; loads the matching data file, `?mode=lod` in the URL), difficulty, players in game, partied players nearby (including you), MF %, terror zone on/off + character level + herald tier (RotW, Hell, terror zone only), ladder/non-ladder, act.

* **Tab 1, item search** - autocomplete over bases, runes, unique and set items. Every monster/rank/area/difficulty that can drop it, with mlvl, P(base), P(magic), P(rare), P(set), P(unique), P(target) per kill, kills per run and P(target) per run. **All probabilities are shown as odds** ("1 in 4,334,276", two decimals below 10, "always" at 1, "-" for none); columns sort by the underlying probability, so descending = most likely first. The default columns are monster (fixed width: long minion lists wrap), area, difficulty, mlvl (monster level = item level of the drops; an area row shows its lowest-highest), chance per kill, kills/run, chance per run and "runs for 50%" (it counts kills while the table is sorted by a per-kill column; hover a cell for 25/50/75/90/95/99%: `ceil(ln(1-q) / ln(1-p))`, `Engine.trialsFor`); "Show quality breakdown" adds P(base/magic/rare/set/unique), act and mlvl. A headline gives the best source per kill and per run, the lowest monster level that can drop the item, and, when nothing is listed, why. "Group by Area" combines every source of an area. Chance per run is the chance of at least one drop: 1 - (1 - p)^(kills/run) for a row, 1 - prod (1 - p_i)^kills_i over the sources of an area (the earlier linear kills x p, capped at 1, overstated common drops). Click headers to sort; filter by text, rank, difficulty, act. For a unique/set item P(target) is the chance of that exact item.
* **Tab 2, popular farms** - the reverse of Tab 1: pick a **farm** (below), or **Other area...** to pick any **area** (difficulty from the bar under the tabs; All = Hell) and optionally one source of it (a regular pack, champions, uniques, minions, a super unique or boss; none = a whole area clear) or a named run. The **Farm** list sets area and source at once (Area and Source are shown only under Other area...): grouped by act: Andariel, Countess, The Pit, Cow Level; Ancient Tunnels, Summoner (boss only / + Arcane Sanctuary ghosts); Travincal council, Mephisto (boss only / + Bremm, 5 council kills / + full council, 7); Chaos (seal pop / full clear); Shenk + Eldritch, Pindleskin, Nihlathak, Baal (`CONFIG.farms`; a boss is its regular kill, a super unique farm is a named run with its minions, the rest are whole area clears); an Area / Source pair that matches a farm (a deep link, say) shows as that farm, and a chosen farm follows the difficulty. The Area lists also include The Worldstone Chamber and Colossal Summit (no spawn list, only bosses). Named runs (`CONFIG.runs`: super uniques with their own minions and act bosses from any area, plus monster types killed at every rank in the run's own area, plus areas cleared in full; listed under that area): The Pit (full clear of Pit Level 1 and Pit Level 2), Ghosts + Summoner (every ghost in Arcane Sanctuary: regular, champion, unique, minion), Countess, Travincal council (Ismail, Geleb, Toorc), Mephisto + Bremm Sparkfist, Mephisto + the Durance of Hate 3 council (Wyand, Maffer, Bremm; only Bremm has minions), Shenk + Eldritch (Bloody Foothills, Frigid Highlands), Pindleskin and the Chaos Sanctuary **seal pop**: Grand Vizier of Chaos, Lord De Seis and Infector of Souls (1 kill each) with their own minions (superuniques.txt MinGrp / MaxGrp + 1 per difficulty, the class's minion1: 11 Storm Casters, 7 Doom Knights and 11 Venom Lords in Hell), then Diablo's regular kill (no quest row); nothing else in the area. `Engine.runSources(ctx, run, diff, list)` returns their rows, with each super unique's minions as rows of their own (in a full clear they are merged into the area's minion rows). The table lists what it drops, best first: uniques, set items, runes, charms and jewels, bases (Show: tick any of these kinds, default all but bases; potions, throwing potions, arrows, bolts, the plain Key and the Town Portal / Identify scrolls and tomes are never listed, the Terror / Hate / Destruction keys and the Scroll of Knowledge are; item text filter, row limit), with the item's base, chance per kill (an area clear: the kill-weighted average), kills/run (one source), chance per run and runs for 50%. Per-run chances are exactly Tab 1's (at least one drop: 1 - prod (1 - p_i)^kills_i over the sources of the clear), so clicking a row opens Tab 1 on that item with the same numbers. Herald rows have no per-run chance and are left out. `Engine.dropsOf(ctx, src, mf)` returns every target's per-kill chance for one source in one pass (same leaf walk as `chanceFor`, verified identical); an area takes a few ms. Hovering an item name (here and in tab 1's headline) shows an in-game style tooltip: name and base in the drop colour, set, type and tier, required level, quality level, max sockets (no stat lines yet: `build.py` does not export the unique / set item properties). Link: `?t3a=<area id>&t3m=<source key or run|<run id>>&t3k=<kinds, comma separated>` (seal pop: `?t3a=108&t3m=run|sealpop`).
* **Tab 3, item builder** - pick an item **type** (Boots, Circlet, Sword, Wand, Auric Shields, ..., with the data's own names; the abstract groups such as "Any Armor" come last) or one specific base, optionally a tier (normal / exceptional / elite). The page then shows:
  * **Affix table** for the type: every prefix, suffix, automagic row, staff-mod skill and the rows of non-magic items - `socket` (sockets of normal / superior items), `ethereal`, `superior` (one row per qualityitems.txt bonus) - that can roll on any base of the type (engine `builderCatalog`, same eligibility as `eligible`), with its description over all tiers (`+10-20% Faster Cast Rate`), affix level, required level, class restriction, the group it excludes (affixes of one group never appear together; the group is named after its first stat), magic-only or rare-allowed, the item levels at which a base can roll it (`20+`, or a window `24 to 35` for affixes with a max level and staff skills, whose tier depends on the item level) and the **odds of the affix appearing** on a random base of the selection at the chosen item level (default 85): magic exact (the magic split with the group exclusion), rare exact too (`rareExact`, see "Rare odds" below, adding up each affix's chance of being drawn); normal / superior / low exact (automagic, staff skills, sockets, ethereal, superior bonus). With Quality on Auto the table has one odds column each for normal, superior, magic and rare (low quality is the normal column minus sockets and ethereal; pick Low to see it); a forced quality shows that one column and only the rows possible at that quality (normal, superior and low items have no prefixes or suffixes). The `Quality` column abbreviates where a row can occur (L N S M R). A base that cannot roll the affix counts 0. By default the figure is the plain average over the type's bases (each base counted equally; the column header says "avg"). Choosing an **Area** (and optionally one **Monster** in it) weights each base by its share of the type's drops from those sources (`baseDropWeights`: the sources' drop distributions at the global difficulty, players, terror zone and mode, several sources weighted by kills per run; bases that cannot drop there get 0; header says "weighted"). Hovering an odds cell lists the odds on each base (and the weights). Filter by text, side or "available at this item level". The Area/Monster selectors also limit the farm search.
  * **Your item**: click affixes to add their stats. Each stat gets a number box and a range slider from the stat's lowest to its highest value over all tiers on the type; the requirement is "stat >= value" (stats where lower is better, such as `Requirements -20%`, use "<= value"). Conflicts are explained: a stat no base can roll, two stats that only come from one affix group, a magic item needing more than 1 prefix and 1 suffix (a rare allows 3 + 3 within its 3-6 affixes), a magic-only affix on a rare (Jeweler's, Chromatic-class automagic rows), stats that never share an item level window. Automagic rows and staff skills use no prefix/suffix slot (one automagic row, up to 3 staff skills). The quality is chosen automatically: low, normal (white), superior, magic and/or rare, whatever the selection allows; "Quality" can force one (Auto / Low / Normal / Superior / Magic / Rare).
  * **Results**: per feasible quality (low, normal, superior, magic, rare; qualities the selection rules out are left out) the lowest item level that makes the combination possible (and the base that needs it), the item level window (an upper bound exists when staff skills are involved), and the required character level of the finished item = max(base requirement, requirements of the cheapest affix tiers satisfying the sliders). A per-base breakdown (expandable) shows the same per base plus its share of the best farm source. These come from `comboAnalysis` / `planCombo`: a structural check (positive probability) over item levels from the base's level to 99, evaluated with the engine's own `eligible` pools, so they are exact and instant. (Item levels below a base's own level are not offered; the affix level formula clamps there anyway.) Not modelled: `Requirements +#%` affixes changing the final requirement, strength/dexterity requirements.
  * **Best places to farm**: every monster/area ranked by the chance per kill that **any base of the type** drops with the combination, with one column per feasible quality (P(low), P(normal), P(superior), P(magic), P(rare)) plus the total and the per-run odds (`affixSearch` over all the type's bases: sum over bases, so it equals the sum of the per-base searches; pools that are structurally impossible are skipped, which does not change any result). The global selectors (difficulty, players, MF, terror zone, character level, act, mode LoD/RotW) apply. Every quality is exact, rare included (so a combination the game can roll never shows as "no source", however rare it is); the search runs in a Web Worker. Sockets of white items depend on the game difficulty (cap 3 / 4 / 6), so the global Difficulty selector applies to them (the item level analysis uses Hell when it says All). Choosing one area ranks by per-run chance. Herald rows (RotW, Hell, terror zone) are listed with their per-kill chance but have no per-run odds and are left out of the full-clear totals; clicking one opens Tab 1 with the herald rank filter instead of an area.
  * **Best item level**: under the card's All picks line, the item level that maximises the odds of all picks per quality (`Engine.ilvlCurve(codes, conds, qualities, weights, o)`: `cardOdds` at item level 1..99; per quality the 99 odds, `first` = lowest level with odds > 0, `best` = argmax (lowest on ties), `lo`-`hi` = the contiguous band around it within 5% of the best), with a log-scale chart (one line per quality, the current level marked, hover shows the odds, click sets the item level). Often below 99, since higher levels add competing affixes and bases. It is per item of that quality (average over the bases that can drop at the level, or area-weighted like the card); the farm table also includes the quality chance, MF and the base mix, so it stays the answer for where to farm. The curve does not depend on the item level, so it is recomputed (own worker) only when the picks, bases, quality, area or difficulty change. The farm summary adds "best monster level per kill": the rows grouped by the item level they roll at (monster level, capped at 99), the best per-kill chance of each.
  * **Shareable link**: the page keeps `?t2=<type code>` (or `b2=<base code>`), `tr2`, `il`, `q=low|normal|sup|magic|rare`, `a=<stat key>:<min>` (repeatable) in the URL (plus `mode=lod` / `diff` when set), for example `?t2=boot&a=%2B%23%25%20Faster%20Run%2FWalk:20&a=Fire%20Resist%20%2B%23%25:30`. The old deep link `?q2=circlet&ql=magic&c=%2B%23%25%20Faster%20Cast%20Rate:20` still works (type or base text match; `ql` = quality).

## Formulas implemented

**Treasure classes** (`engine.js: dist`). Entry probability is Prob / (sum Prob + NoDrop'). Positive Picks k: P(leaf at least once) = 1-(1-s)^k, where s is the per-pick chance (nested TCs multiply). Negative Picks: guaranteed drops, entry i is rolled |Prob_i| times in order until |Picks| rolls are used. The Unique/Set/Rare/Magic factors of nested TCs combine with **max** (decompiled `TreasureClassDropper`, PureDiablo). Monster TC upgrade: highest TC of the same `group` with `level <= mlvl` (top-level TC only; bosses are not upgraded unless terrorized, as in the data guide). Names like `weap72`/`armo66`/`bow45`/`mele30` are generated: all spawnable items of that item type (including child types) whose qlvl is in `(N-3, N]`, weighted by the `Rarity` column of ItemTypes.txt for the item's first type (`type`), values <= 1 forced to 1 (quest items excluded). There is **no check of the base item's qlvl against the monster level**: a level-81 Hell Bovine can drop Archon Plate (qlvl 84) via `armo84`. Nested TCs are fetched with level 0, so only the top-level TC is group-upgraded. Source: D2MOO `DATATBLS_CreateItemTypeTreasureClasses` (MonsterTbls.cpp), `DATATBLS_GetTreasureClassExRecordFromIdAndLevel`, `D2GAME_DropTC_6FC51360` (Items.cpp). `ConditionCalc` is not evaluated (no row uses it) and of `DropConditionCalc` only `cond('Difficulty', normal|nightmare|hell)` is understood (the six PreCrafted Sunder uniques; any other expression would exclude the row); `first/lastLadderSeason` are honoured with `CONFIG.currentSeason = 15` (ladder season 15, from 2026-08-21; bump it each season). A ladder-only window that has ended opens the item to non-ladder. In the RotW tables the nine uniques reworked in patch 3.3 (Bane Ash, Gravenspine, Bloodletter, The Ward, ...) are season 15/15 and the Angelic Raiment set 15/16, so on RotW non-ladder they cannot drop this season (each has a single row, with the new stats; there is no old-stats row to fall back to); the Sunders (2/2) are open to non-ladder. The LoD tables have no gating.

**Per-kill drop cap** (`CONFIG.dropCap = 6`, `engine.js: dist`). The game's drop routine (decompiled `TreasureClassDropper`, https://gist.github.com/SeanSullivan86/e912b40bb85f9822b9ef507d91534c88) stops a kill after 6 items (`if (*itemCount >= maxItems) return;`). This limit is hard-coded in the game, not in the tables, and is assumed to still be present in 3.3. Drops happen in order (depth-first, picks in sequence, negative-Picks entries in listed order); gold, potions, scrolls and keys count, non-item entries (quest flags) do not. It matters for Duriel (about 18 items uncapped, roughly 3x overstated) and a few percent for Countess, Mephisto, Diablo, Baal, Andariel, more with more players. It is computed exactly: a TC is a linear map on the number of items dropped so far (0..6); sequences multiply the matrices, a pick is a mixture, and per leaf the matrix of "this leaf not produced" is kept so P(leaf at least once) = 1 - (row 0 of that matrix summed). TCs whose maximum possible item count is <= 6 use the plain formula. `CONFIG.dropCap = null` (or 0) reproduces the uncapped numbers exactly.

**NoDrop with players**: `NoDrop' = floor(Items / (1/(NoDrop/(NoDrop+Items))^N - 1))`, `N = nearbyParty + floor((players - nearbyParty)/2)`.

**Item quality** (`quality`): per base, checked Unique > Set > Rare > Magic > Superior > Normal > Low, each failure falls through.
Exact game integer math (D2MOO `D2GAME_DropTC_6FC51360`, Items.cpp; C division truncates toward zero): `nLevelDiff = mlvl - qlvl`; `p = (Ratio - nLevelDiff/Divisor) << 7` (the division comes first and is truncated); with MF != 0, `D = MF + 100`, `p = 12800*(Ratio - nLevelDiff/Divisor)/div` where `div = D` for magic and, for D > 110, `50*(5D-500)/(D+150)+100` (unique), `100*(5D-500)/(D+400)+100` (set), `200*(3D-300)/(D+500)+100` (rare) - equal to `100 + trunc(MF*dim/(MF+dim))` with dim 250/500/600 (`CONFIG.mfDim`), cutoff MF > 10 (`CONFIG.mfThreshold`; the data guide's "exceeds 110%" counts the `item_magicbonus` baseline of 100); `p = max(p, Min)` (unique/set/rare/magic); `p -= p*TCfactor/1024`; success if `p <= 0` or `rand(p) < 128`, i.e. chance `= 128/p` (1 if p <= 128). Superior/normal use `HiQuality`/`Normal` with their divisors, no MF, no Min, no TC factor; failing normal gives low quality. MF is applied to unique/set/rare/magic only. itemratio row: Version 1, Uber (exceptional/elite) and Class Specific flags. Unique success with no eligible unique (spawnable, not disabled, lvl <= ilvl, ladder rules) becomes rare (magic if the type cannot be rare); set success with none becomes magic. Chance of one specific unique/set = quality chance x rarity / sum rarity of the eligible ones for that base. Item types flagged "Magic" (rings, amulets, jewels, charms) are always at least magic; "Normal" types (runes, gems, potions) are always normal. Quest-type misc items (keys `pk1`-`pk3`, essences, organs, statue pieces `ua1`-`ua5`, shards `xa1`-`xa5`, ...) have **no quality**: `build.py` flags (`nq`) every misc item whose type chain has none of the ItemTypes Rare/Magic/Normal flags, and `quality()` returns all zeros for them, so their whole chance is P(base) (the boss TCs' Magic=1024 does not make a key magic) and they are not counted as magic in `qualityTotals`.

**Monster level**: Normal = monstats `Level`; Nightmare/Hell regular monsters = the area's `MonLvlEx(N/H)`; act bosses = monstats `Level` per difficulty (Andariel 75, Mephisto 87, Diablo 94, Baal 99 in Hell); super uniques = the area level of their (hand-mapped) area (Normal uses the class monster's `Level`) **plus the unique bonus +3** (Hell Pindleskin 86, Hell Countess 82, Normal Rakanishu 8, Normal Cow King 31; in a terror zone `tzLevel(...) + 3`, which may exceed the zone max). Act bosses get no bonus. Champions +2, uniques +3, unique minions +3 (`CONFIG`). Radament, The Summoner, Nihlathak and Griswold are both super uniques and act bosses in the tables; only the act-boss row is kept (no bonus). Terror zone: `mlvl = max(base, clamp(clvl + boost_level, bound_incl_min, bound_incl_max))` per difficulty from `desecratedzones.json` (Hell: 70..96, +2), then the rank bonus is added and may exceed the max. Terrorized act bosses get the unique bonus too, with their own level as the floor: `max(own, zone level + 3)` (Hell: Andariel 93 at clvl 88, Diablo stays 94 at clvl 85, Baal 99); Radament, Griswold and Nihlathak get a further +3 after that (`CONFIG.tzBossExtra`), so they reach 102 at clvl 94+ (Basin wiki "Terror Zone", Zax's terror zone loot guide on the Blizzard forums); outside a terror zone act bosses keep their own level; the `TreasureClassDesecrated*` / super unique `TC Desecrated` columns replace the normal TC when present. Only levels listed in the zone file are flagged as terror-zone areas.

**Item generation rules (affixes, rares, staff mods, automagic)** - re-verified against the D2MOO decompilation (https://github.com/ThePhrozenKeep/D2MOO, files named below); the constants live in `Engine.CONFIG` with the same citations, and `python test_engine.py` checks the engine against an independent Python re-implementation (`Rules` in `test_engine.py`).

* **Affix level** (`affixLevel`; D2Game `ItemsMagic.cpp ITEMS_ComputeCraftedMagicAffixLevel`): `ilvl = max(item level, qlvl)`; `alvl = ilvl + magic lvl` if the base has one, else `ilvl - floor(qlvl/2)` (or `2*ilvl - 99` once `ilvl >= 99 - floor(qlvl/2)`), clamped to 1..99. Verified, unchanged.
* **Affix eligibility** (`eligible`; `ITEMS_RollMagicAffixesNew`, `ITEMMODS_CanItemHaveMagicAffix`, `ITEMMODS_AffixPlayerClassisCompatible`): spawnable, frequency > 0, version, `level <= alvl`, `maxlevel` 0 or >= alvl, the base's type chain contains an `itype` and no `etype`, `rare` = 1 when the item is rare, a class-specific base only takes its own class's affixes, and the item may not already carry an affix of the same `group` (prefixes and suffixes share the check). Verified. **Socket affixes** (Mechanist's `sock` 1-2, Artificer's `sock` par 3, Jeweler's `sock` par 4; itypes weap/shld/helm/tors (+circ for Mechanist's), etype thro) do roll, on bases that can hold sockets. Eligibility: `ITEMMODS_CanItemHaveMagicAffix` (D2Common `ItemMods.cpp`) tests `ITEMS_CheckIfSocketable(pItem) && ITEMS_GetMaxSockets(pItem)` before it looks at the first property (`pPropertiesTxtRecord->wStat[0] != STAT_ITEM_NUMSOCKETS`); the decompiled branch, read literally, would reject every socket affix, which contradicts the game (magic and rare sockets drop) and the tables (Mechanist's is `rare`, Artificer's/Jeweler's are magic-only), so the rule used is: a socket affix needs a base with an inventory (`hasinv`) and `ITEMS_GetMaxSockets` > 0. Count: `ITEMMODS_PropertyFunc14` (properties.txt `sock` func 14): `nMaxSockets = min(invwidth * invheight, ITEMS_GetMaxSockets(pItem))`, the value is `min + rand(max - min + 1)` from the affix, `<= 0` -> the param (`nLayer`), then `nSockets = clamp(value, 1, nMaxSockets)`. `ITEMS_GetMaxSockets` (D2Common `Items.cpp`): the first type's `MaxSockets1` (item level <= threshold 1, 25), `MaxSockets2` (<= threshold 2, 40) or `MaxSockets3`, capped by the base's `gemsockets`. So rares can only get 1-2 sockets (Mechanist's), magic items 1-2 / 3 / 4, always limited by the base and its item level (a Monarch needs item level 80+ to have Jeweler's in reach: affix level 55). `Socketed (#)` is a selectable stat in the Tab 3 item builder. `build.py` exports `gs` (gemsockets, 0 without inventory) and `sz` (width * height) per item and `ms` (MaxSockets1/threshold1/MaxSockets2/threshold2/MaxSockets3) per item type. (A previous version of this README said these affixes never roll; that was wrong.)
* **Affix weight** (`ComputeAffixFrequency`): `frequency`, but for bases with a `magic lvl` > 0 (staves, wands, orbs, circlets) `frequency * affix level`. **New**; verified in D2MOO, ASSUMED to hold in D2R (`CONFIG.affixWeightByLevel`). D2MOO's draw is `rand(total + 1)`, so the last eligible row weighs `frequency + 1`: ignored (relative effect 1/total).
* **Magic items** (`sub_6FC4D5E0` in `D2Game/src/ITEMS/Items.cpp`): the prefix roll succeeds 1/2; if it fails the suffix is forced, else 1/2: both 1/4, prefix only 1/4, suffix only 1/2 (the old Arreat Summit split, now verified from code). A side without an eligible affix returns 0 and the other side is forced.
* **Rare items** (`D2GAME_RollRareItem_6FC53360` in `ItemsMagic.cpp`, the expansion-format path): the number of affixes is `{3,4,4,5,5,5,6,6}[rand & 7]`, so **3: 12.5%, 4: 25%, 5: 37.5%, 6: 25%** (mean 4.75), **not** uniform 3-6 (the 1.00-format path, not used by LoD/RotW, is uniform 4-6); jewels 3 or 4 (50/50). Each step takes prefix or suffix 50/50 while both sides have room (max 3 each, `ITEMS_MAX_MODS`), otherwise the open side; a roll that finds nothing eligible closes that side and does not use up a step; every pick excludes the groups already on the item. Only `rare = 1` affixes. **Changed**: the count distribution (mean 4.5 -> 4.75) and the step/closing rule.
  * **Rare odds are computed exactly** (`rareExact` in engine.js), not sampled: the loop above is summed over all its outcomes. A pick takes an affix with chance weight / (weight of the side's affixes whose group is still free). The groups that matter (one of their affixes meets a condition) are followed one by one; every other group only lowers the weight left on its side, and groups of equal weight are interchangeable, so only how many of each weight are gone is kept. A side's picks only see its own pool, so each side is stepped alone (at most 3 picks) and the two meet through the prefix / suffix order of the draws; a group on both sides (RotW group 307, not spawnable at present) is handled by noting before which draw the other side took it. Per side the chance of each set of conditions met is kept (the value rolls of the affixes drawn), and the sides join over pairs of sets, so every term is positive and tiny odds (a 5-affix rare of about 1 in 1.3 million per rare boots) keep their digits. Small pools where a side could run out of groups use `rareSteps` (both sides in one state; same result). Before, rare odds were a Monte Carlo of 20k-200k rolls per pool, which returned 0 for anything rarer than about 1 in the roll count.
* **Staff mods** (`sub_6FC52410` -> `sub_6FC52650` in `D2Game/src/ITEMS/Items.cpp`; `ITEMS_GetStaffMods` in `D2Common/src/Items/Items.cpp` reads the item's first type only): applied at the end of every low/normal/superior/magic/rare/crafted item roll, never for unique or set items. Item types with a `StaffMods` class code: scepter (pal), wand (nec), staff (sor), orb (sor), voodoo heads (nec), primal helm (bar), pelt (dru), cloak (ass), hand to hand 2 (ass); **RotW adds knife, warlock item and grimoire (`war`)**. Count: roll 0-99, >90 three, >70 two, >30 one, else none (P(0..3) = 31/40/20/9 %). Tier base from the *item level of the drop* (not the affix level): > 36 -> 5, > 24 -> 4, > 18 -> 3, > 11 -> 2, else 1. Each skill: tier = base +1 (19%) / +0 (50%) / -1 (20%) / -2 (11%), at least 1; the skill is `class first skill id + 5*(tier-1) + rand%5` (the class's 30 skills in id order, five per tier; no `reqlevel`, no other level check; so a tier-1 skill such as Teeth only appears at item level <= 18 and a tier-6 skill needs item level > 36). Up to 6 tries find a skill that is not already picked and whose `itypea1` fits the item (Poison Dagger needs a knife, so effectively never on a wand; the all-six-tries-failed fallback posts the last roll anyway, probability (rejected/5)^6); value +1 (60%), +2 (30%), +3 (10%) (always +1 on low quality). Staff mods are independent of the magic/rare affixes (no skipping, no interaction), so a condition like "+2 to Poison Explosion" is exact for magic (staff outcome enumerated as a condition bitmask, combined with the exact affix enumeration) and exact in expectation for rare. `statList` offers each staff skill of the base's type as `+1-3 to <skill> (<Class> Only)`; `build.py` exports `types[..].sm` and the per-class skill lists (`data.staff`).
* **Automagic** (`D2Game/src/ITEMS/ItemMode.cpp`, item finalisation, `ITEMS_RollMagicAffixes(..., wAutoPrefix)`): after the regular affixes of an inferior/normal/superior/magic/rare/crafted item (not unique/set) one row of the item's `auto prefix` group is attached (forced roll, spawnable *not* required, the usual level/`maxlevel`/`itype`/`etype`/class checks, weight as above). **Changed**: on a *rare* item only `rare = 1` automagic rows apply (35 of the 44 RotW rows, 29 of 36 LoD rows; e.g. Archer's is magic-only); automagic now also honours itype/etype/class (every row says `armo`/`weap` today, so nothing moves from that).
* **Low / normal / superior items: sockets, ethereal, superior bonus** (`CONFIG.nonMagic`; D2MOO `ItemMode.cpp sub_6FC4C5F0_End`: quality and its bonus, then `ITEMS_MakeEthereal`, then sockets, then automagic):
  * **Sockets** (`Items.cpp sub_6FC4D6B0`): normal and superior items only (low returns at the first line; magic and rare get sockets only from the socket affixes above). The base needs an inventory and may not be stackable (so no javelins, throwing weapons, quivers). `nMaxSockets` = `ITEMS_GetMaxSockets` (type MaxSockets by item level 25 / 40, the base's `gemsockets`, inventory size) capped by the game difficulty (Normal 3, Nightmare 4, Hell 6). The chance is `rand % 100 < 33`, a flat **33%** whatever the difficulty, type or item level, and the count is uniform 1..nMaxSockets (a white Monarch in Hell at item level 60 or 85: 8.25% each of 1, 2, 3, 4 sockets; item level 30: 11% each of 1-3; Normal difficulty: 11% each of 1-3).
  * **Ethereal** (`Items.cpp ITEMS_MakeEthereal`): a flat **5%**, independent of the sockets (ethereal is rolled first and the socket code never looks at it, so ethereal + socketed happens). Weapons and armor with `ITEMS_HasDurability` (not `nodurability`, durability > 0) on normal, superior, magic, rare and unique items; **never low quality, never set items** (the user confirmed this for D2R). D2R's tables mark every bow, crossbow and Amazon bow `nodurability = 1` (like the Phase Blade and the throwing potions), so **bows and crossbows are never ethereal**. The Phase Blade and the throwing potions are never ethereal either; jewelry and charms never are (not weapon or armor); javelins and throwing knives / axes can be (durability set, the code has no stackable test). So every weapon and armor can be ethereal except bows, crossbows (incl. Amazon bows), the Phase Blade and the throwing potions (the test run prints the list per item type). The x1.5 defense / damage and the lowered durability of ethereal items are not modelled, ethereal is only a flag.
  * **Superior bonus** (`ItemsMagic.cpp sub_6FC54690`, `ITEMMODS_CanItemBeHighQuality` in `ItemMods.cpp`): exactly one `qualityitems.txt` row, uniform among the rows the item qualifies for, each mod a uniform integer min..max; a row can carry two mods (row 3 = +1-3 attack rating and +5-15% enhanced damage). Armor (incl. shields, boots, gloves, belts, circlets, pelts, primal helms, grimoires): rows {2, 4, 7} = ED 5-15% | max durability +10-15% | both, 1/3 each. Weapons: rows {0, 1, 3, 4, 5, 6} = attack rating 1-3 | enhanced damage 5-15% | both | durability | AR + durability | ED + durability, 1/6 each. Throwable or `nodurability` items (bows, crossbows, javelins, throwing weapons, Phase Blade) only the first 4 rows: {0, 1, 3}. `build.py` exports the rows (`data.qi`) and each item's eligible rows (`sq`, from the item kind columns of qualityitems.txt and the first item type), plus `nd` / `hd` / `th` / `st` flags (nodurability, has durability, throwable, stackable). The durability bonus is shown as `Increase Maximum Durability #%`; attack rating, enhanced damage and enhanced defense reuse the stats of the affixes, so `+% Enhanced Defense >= 15` is met by either source (P(ED >= 15 | superior armor) = (2/3)(1/11)).
  * **Low quality** (`sub_6FC55270`): Crude / Cracked / Damaged / Low Quality, 1/4 each; never socketed, never ethereal; still gets the automagic row and staff mods (always +1 on low quality). The damage, defense and durability penalties are not modelled.
  * In the engine these are independent sources of conditions next to the affixes (`extrasDist`: a bitmask distribution of the stat conditions met by the socket roll, the ethereal roll and the superior row, OR-combined with the staff mod distribution), so `Socketed (#) >= 4` with `Ethereal` and `+% Enhanced Defense >= 15` combine exactly for every quality.
* **Still assumed / not confirmable from D2MOO (1.10)**: D2R-only balance changes to any of the above; the Warlock (class index 7; D2MOO's 1.10 code uses 7 as "no staff mods") for staff mods; `affixWeightByLevel` in D2R; the item level used by staff mods for monster drops is taken as the monster level (`src.mlvl`); the unique/set/crafted paths are not modelled.

**Per-run estimate (one full clear; `areaRun` in engine.js, rules from the D2MOO decompilation of LoD 1.10-1.14, not verified for D2R)**: the game makes one spawn roll per 3x3 subtiles of each room (173 per 8x8-tile room, about 2.7 per tile; `D2GAME_PopulateRoom_6FC67190`) and spawns a pack when `rand % 100000 <= MonDen` (capped at 10000). Area size: caves (DrlgType 1) use the average number of populated cells (Populate 1 presets) of SizeX x SizeY tiles that the cave generator makes (levels.txt SizeX/SizeY is only the 200x200 bounding box there). `tools/maze_cells.py` replays `DrlgMaze.cpp` (`DRLGMAZE_GenerateLevel`, `DRLGMAZE_AddAdjacentMazeRoom`, `DRLGMAZE_MergeMazeRooms`, `DRLGMAZE_PickRoomPreset`, `DRLGMAZE_RollAct_1_2_3_BasicPresets`, the `ScanReplaceSpecialPreset` / `AddSpecialPreset` entrance / exit / waypoint / chest / boss presets, the Act 2 sewer / lair / tomb layouts, Hell1-3 lava, ...) for 2000 seeds per level and difficulty (`random.Random(level * 1000 + difficulty)`, so the result is reproducible) and writes `tools/maze_cells.json`: mean cells, mean populated cells and the expected count of every lvlprest row; the D2MOO enum values and special-preset tables it needs are frozen into the script (no D2MOO checkout needed), and the file records the seeds and a digest of the input tables (`build.py` warns and falls back, `test_engine.py` fails, when the tables changed). `build.py` writes the populated mean as `geo.cells` (+ `geo.sim` 1; Populate flags of the mode's own lvlprest.txt, LoD differs in four rows). The simulation moves several caves a lot from the old `Rooms` + `max(2, warps + waypoint)` x 0.5 rule: Tal Rasha tombs, Sewers 1 (13.7 cells), River of Flame (33 cells, 10.7 populated), Harem / palace cellar / spider caves / Stony Tomb (always 4), Claw Viper Temple 2 (1), Flayer dungeons (4 populated), Hell1-3 (3 populated). That rule (`mazeSpecialCells`) is kept only as the fallback for a maze level without a simulated value. **Tal Rasha's Tomb** (levels 66-72, one merged row) describes the TRUE tomb, the one with the orifice: all seven levels are simulated as the staff tomb (`DrlgDrlg.cpp`: x3 rooms, about 18.2 cells; a plain tomb is 6.4, the boss tomb 12.7), identical so the merge by `DUP_OF` still works; the kills per run of that row are about 3x a plain tomb. Other areas use levels.txt SizeX/SizeY, and Frigid Highlands / Arreat Plateau / Frozen Tundra the 64x160 the Act 5 linker forces (`DrlgOutRoom.cpp`). About one room of rolls is lost per warp / waypoint (WarpDist). Placement is two factors. (1) A per-level `pl` from the real map layouts (`tools/floor_share.py`, run by `build.py` on `excel/tiles/*.ds1|*.dt1`): each populated preset room (8x8 tiles, a cave cell up to 12x12 is one room) gets its share f of walkable subtiles (floor tile present and no wall bit in any floor / wall / shadow tile's collision flags, the filler floor of FillBlanks presets blocks, `D2Collision.cpp`), the game tries 20 random spots per pack (`MonsterRegion.cpp sub_6FC66260`) so a room places with 1-(1-f)^20, and `pl` is the roll-weighted mean over the level's rooms (caves: the lvlprest rows weighted by their expected count in the simulated generator, `tools/maze_cells.json`, specials and themes included, Populate 0 rows out; without the file the 15 ordinary direction cells of the level type with equal weight, or the level's fixed / hardcoded presets; preset levels: their preset; Chaos Sanctuary: the 6 of 25 cells that hold Diablo presets, the rest is Populate 0 lava; Act 3 jungles: the 15 river cells). Because 20 tries almost always find a spot, `pl` is near 1 except in rooms that are mostly void or wall. Open outdoor levels (wilderness, deserts, mesas, Kurast, Cow Level; generated fill) are not modelled and get `pl` = 1. (2) The rest is one global `placeFactor` = 0.56 (**not from the code**: losses the layout does not explain), calibrated on the only measured count found (Cow Level Hell, ~516 cows per run in a LoD-era guide; the rules alone give ~924). The Cow Level has `pl` = 1, so the factor is unchanged by the layout step. Monster types: the game picks min(NumMon, 13) entries of mon (Normal) / nmon (NM/Hell) uniformly without replacement (first pick re-rolled for a ranged type with `rangedspawn`), keeps `isSpawn` ones, and picks each pack by Rarity; the engine averages exactly over every possible pick. Regular pack = MinGrp..MaxGrp (1 for Fallen / Scarab bases), `sparsePopulate`, `placespawn` swap (79%), plus PartyMin..PartyMax party minions per member, alternating minion1 / minion2 and counted as their own monster type. Champion / unique packs replace regular ones: while below MonUMin a pack in room r of R is one with chance r/R, below MonUMax 6% more (`MONSTERCHOOSE_GetBossSpawnType`, expected value computed step by step); Normal takes their type from umon, NM/Hell from the area types by Rarity; 20% are champion packs of 2-4 champions (monumod constants), else a unique with 3-6 minions (minion1, else its own type). Bosses and super uniques = 1 kill per run (separate rows). Super unique minions (`MonsterUnique.cpp D2GAME_SpawnSuperUnique_6FC6F690` -> `D2GAME_SpawnMinions_6FC6F440(..., 1, MinGrp, MaxGrp)`): MinGrp / MaxGrp of superuniques.txt are each raised by the difficulty (+1 Nightmare, +2 Hell) when both are non-zero, the count is MinGrp + rand(MaxGrp - MinGrp + 1) of the class's `minion1` (else the class itself), so a minion row of (MinGrp + MaxGrp) / 2 per run: Council members 2 / 3 / 4 for Ismail / Geleb / Bremm (Travincal, Durance 3), 0 for Toorc / Wyand / Maffer, the Chaos seal bosses 9 + 2 own-type (Infector, Vizier) and 5 + 2 doomknight1 (De Seis), each Baal wave from its own row. The same function then hard-codes extra minions for four of them (`switch (dwHcIdx)`, `sub_6FC6A230` spawns `nCount` owned copies): Radament 2-6 skeleton5 (mean 4) + four skeleton mages, Shenk (Siege Boss) 20 x minion1, Nihlathak 20 x the Halls of Vaught variant of minion1 (`D2Common_11063`), Baal Subject 2 (Achmel) 10 x skmage_cold3. The Baal waves are spawned by the throne AI (`AITHINK_Fn134_BaalThrone`, skill Baal Monster Spawn with the super unique id -> `D2GAME_SpawnPresetMonster_6FC66560` -> the same `D2GAME_SpawnSuperUnique_6FC6F690`), so the generic rule applies to them (Colenzo with Warped Ones, Bartuc with Council Members, ...); the skill itself has no decompiled handler. Minion rows use the area level + `minionOffset` and the minion monster's own treasure class; a minion type the area already has as a unique's minion is merged into that row; preset super uniques are not counted twice (`pre` excludes them). **Pandemonium** areas Matron's Den, Forgotten Sands, Furnace of Pain and Uber Tristram (133-136) only open in Hell (`ho` 1 in data.json: no sources for Normal / Nightmare even though levels.txt has monsters for them). The portal keys (pk1-pk3) only drop from Hell treasure classes (Countess Item (H), Summoner (H), Nihlathak (H)); D2MOO parses the portal recipes (`HoradricCube.cpp`, CUBEOP_UBERDUNGEON / CUBEOP_UBERTRISTRAM) but does not contain the code that opens them and the recipes have no `min diff` (the Colossal Summit recipe has, enforced in `PlrTrade.cpp`), so this restriction is game knowledge, not a decompiled check. Uber Tristram's bosses are not modelled. Preset monsters (`tools/preset_monsters.py`, run by `build.py`; per level `pre`, `pb`, `pk` in data.json): the map files list monsters at fixed spots (.ds1 unit list, `DrlgPreset.cpp DRLGPRESET_ParseDS1File`; the id indexes the file's act in monpreset.txt, whose Place is a super unique, a monster or a monplace.txt class); the game spawns them with their room, before the random population, with no MonDen roll and no placement loss (`SUNIT_SpawnPresetUnitsInRoom` -> `D2GAME_SpawnPresetMonster_6FC66560`). Per level the extractor sums the units of the presets the level uses (File roll; maze levels: the expected count of every lvlprest row in the simulated generator, so themes, entrance / exit and chest / boss presets are included; without `maze_cells.json` the lvlmaze cells, max(2, rooms/5+1) theme presets and a hand-written list of the special presets; Act 1 wilderness, Act 4 mesas, Travincal and the Bloody Foothills siege strips from the generator code). Classes: fallen / fetish (and shamans) = the level's own variant (`D2Common_11063`, Black Marsh / Tamoe / Pit overrides), tentacles by level, imp / minion groups (Act 5, MinGrp..MaxGrp) in Normal only, `place_reanimateddead` = reanimated horde (counted), dead corpses (`place_dead*`) not counted, `place_unique_pack` = a unique pack (no champion roll) and `place_champion` = a champion pack of a type picked like the random boss packs. Fixed monsters are regular kills with their party minions (`pre`); packs add through the same type pick as the random ones (`pb`); super uniques stay separate rows and act bosses are left out, but unique packs, champion packs and super uniques raise the level's unique count, which starts the MonUMin / MonUMax ramp above zero (`pk`, `bossPacks(..., start)`, `D2GAME_SpawnMonster_6FC6F220` ++dwUniqueCount; a champion pack counts once, its minions are not counted, same as the random packs), so levels with preset uniques get fewer random champion / unique packs. Not modelled (no preset monsters, pl/pk unchanged): generated fill (Act 2 desert, jungles' clearings, Kurast, Act 5 Frigid Highlands / Arreat Plateau / Tundra barricade fill and prisons), and monsters that objects spawn (sarcophagi, evil huts, dead barbarian bodies, chests); placement of `place_group25..100` (no spawn code in the decompilation). The same kill mlvl rules as random monsters apply. Expect about +/-50% per area; open outdoor areas (generated fill) are not corrected for void (pl = 1), and the levels.txt bounding box is taken as the populated area everywhere except Chaos Sanctuary (Forgotten Sands and Halls of Vaught still come out high). `test_engine.py` checks the engine against an independent Python version (`RunRef`, which reads `pl`, `pre`, `pb` and `pk` from the built data) for 23 areas, the ds1 unit parser and the preset rules on known files, the Cow Level calibration, and the floor-share parser on known map files. Constants: `CONFIG.run`.

**Merged rows per area** (`Engine.areaSources`, used by the app): the champions, uniques and minions of one area are shown as one row each ("Champion monsters", "Unique monsters", "Minions"; hover the name for the monster types). Heralds are merged across all terror-zone areas instead (below). In NM/Hell every type of one rank in an area is at the same mlvl and group-upgrades to the same TC, so the per-kill odds are identical and kills/run add up. Rows merge only when upgraded TC and mlvl match; a rank that still splits (mostly Normal, where mlvl is each type's own) lists its members after the label. **Herald rows** merge across areas: one row per tier and mlvl ("Herald tier 3 (mlvl 88)", 16 rows per tier at low clvl, 1 from clvl 83), because the Herald TC depends only on mlvl and tier (see Heralds). The Area column says how many areas the row covers (hover for the list) and the Act column lists their acts; the Act and source filters match any covered area and narrow the shown list. The Herald tier selector has an **All tiers** option (default) that lists tiers 1-5 as separate rows. `Engine.sources` still returns one row per monster type (the tests use it). Areas that are exact copies of an earlier one (same name and every field: the seven Tal Rasha's Tombs 66-72) are listed once, as the lowest id (`Engine.DUP_OF`); kills/run stays per tomb (the true staff tomb, see Per-run estimate).

## Game modes

`excel\base\` is the **Lord of Destruction** mode (not classic) and the root folder is **Reign of the Warlock**. 38 of the 91 tables differ between them, 53 are byte-identical. The differences are mostly new content or retuned values: `treasureclassex` (+220 rows: Herald, Ancient Statue, Worldstone Shard, Uber TCs), `uniqueitems` (+12 rows: PreCrafted/Crafted Sunders, the Ars grimoires; new `disableChronicle` column), `monstats` (herald TC columns, Uber Ancients), `levels` (+Colossal Summit), `misc`/`itemtypes` (+1 row each), `cubemain` (+72), `armor`/`automagic`/`weapons`/`runes`/`sets`/`setitems`/`magicsuffix`/`properties` and skill/state/sound tables (value changes), and a few cosmetic ones. The calculator therefore has **two complete data files**, one per mode, instead of one file with overrides: `data.json` = every table from the root folder (RotW) plus the `rotw` section of `desecratedzones.json`; `data-lod.json` = every table from `excelase\` plus the `expansion` section. Both come from one code path (`build.py: build(mode)`), carry the same `meta` (`gameVersion`, `buildKey`, `built`) plus `meta.mode` (`rotw` | `lod`), and are committed (GitHub Pages serves static files). An earlier version stored only two LoD overrides (`spl` flags for grimoire spawnability and automagic) on top of the RotW data; with 38 of 91 tables different that was wrong (different `Andarielq (H)` factors, no statue pieces or shards, different uniques/sets/affix values, ...). (An even earlier README said only `armor.txt` and `automagic.txt` differ; that came from a bad extract in which 36 root tables were copies of the LoD ones.)

* One engine instance per data file (`Engine.create(data)`); nothing in the engine switches mode. `Engine.CONFIG.gameMode` ('lod' | 'rotw') and `E.mode` just reflect `meta.mode` of the loaded data. The UI "Game mode" selector fetches `data.json` or `data-lod.json` (each cached after the first load), rebuilds the search index, the Tab 3 type list and area list, drops the old results and re-runs the current tab; the Web Worker gets the file name in each message and keeps one engine per file. The header shows the loaded data's game version and mode.
* Heralds are data driven: the `expansion` section of `desecratedzones.json` has no `herald_tiers`, so `data-lod.json` has an empty herald list and `heraldsAvailable` is false (RotW + Hell + terror zone only otherwise).
* Examples of what differs: the 15 Warlock grimoires (`wa1`..`waf`) and their 8 automagic mods and Warlock-class affixes exist only in RotW (they join and dilute the generated `armoN` pools there); statue pieces `ua1`-`ua5` and Worldstone Shards `xa1`-`xa5` have no source in LoD; `Andarielq (H)` has unique/set factor 995 in LoD against 983 in RotW; `desecratedzones.json` bounds come from the `expansion` section (identical numbers today).
* Tests (`python test_engine.py`) read either table folder through the independent Python reference (`Ref()` = root, `Ref("base")` = LoD) and compare the engine on the matching data file: Hell Andariel/Mephisto/Countess/Baal unique/set/rare/magic totals and Harlequin Crest against the base tables, the Andarielq factors, no Warlock affix on an amulet, no statue/shard in the LoD index, no grimoire anywhere in LoD, per-mode armoN pool shares.

## Heralds (RotW, Hell, terror zone on)

Data-driven (`desecratedzones.json` -> `rotw.hell.defaults.herald_tiers`): five tiers with `herald_treasure_class_level_boost` 0/3/6/9/12 (data guide: "boost to the treasure class level of a Herald... not a boost to the item level dropped"), minion counts, unique mod counts, HP/damage boosts and the logistic spawn-chance constants.

* **Herald TC**: monstats `TreasureClassHerald(H)` (465 monsters, e.g. `skeleton1` -> `Act 1 (H) Herald A`; the Normal/Nightmare columns are empty, heralds are Hell only). `build.py` exports it as `m.tc[2].hr`. One herald row is created per area monster type with `CannotHerald` not set; mlvl follows the terror-zone unique rule (+3). The app merges them across areas by (tier, mlvl, upgraded Herald TC).
* **Group upgrade**: the herald TCs are group 41 (`Act N (H) Herald A-C`, levels 67..96, Picks -6), upgraded at `mlvl + herald_treasure_class_level_boost` like any top-level TC. **Data quirk**: the five `Ancient Statue 1-5` TCs are also group 41, all at level 92, so an unrestricted upgrade landing on 92 would resolve to a statue TC (ties go to the last in file order, `Ancient Statue 5`). Nobody has observed a herald dropping a statue piece, so heralds are restricted to the Herald TCs (`upgradeTC(..., only)`). This is observed behaviour, not something the tables say. The tier boost only matters while `mlvl + boost` is below 96, the level of `Act 5 (H) Herald C`.
* **Tier gating of the extra item picks** (`CONFIG.heraldExtraByTier = [null, null, '1 Extra', '1 Extra', '2 Extra']`). Each top-level herald TC lists `Herald Item X` x2, `Herald Item X - 1 Extra` x1 (Picks -1: one more item pick), `Herald Item X - 2 Extra` x1 (Picks -2: two more) and `Cpot` x2; each `Herald Item` pick holds `Sunder Charms` at 2/407. Taking every entry (5 item picks) does not match the published odds for PreCrafted Flame Rift from heralds (1:342 tier 1-2, 1:228 tier 3-4, 1:171 tier 5); 1-(1-p)^n with p = (2/407)(30/101) and n = 2, 3, 4 item picks does exactly. So the game gates the extras by tier: tiers 1-2 drop only the base entries, tiers 3-4 add `- 1 Extra`, tier 5 adds `- 2 Extra` (not both). The gating is hard-coded (not in the tables), verified against the published odds; it is also what the 3.2 note "tier 3 and 4 have twice the increased chance, tier 5 three times" amounts to, so the old "herald bonus path" with an unknown base chance (`heraldSunderBonusBase`, the "Herald Sunder bonus base %" input) is gone. The engine gives 1 in 342.8 / 228.7 / 171.7 (1 player, table path; the 6-item cap does not change them, the MF path through unique grand charms adds only ~5e-6 to 1e-5 per kill). Herald Sunder chances do not scale with players (the Herald Item TCs have NoDrop 0).
* `Herald Charm 1-10` TCs exist but nothing references them (probably the hard-coded "something desirable" fallback); they are not modelled and not counted as a source.
* **Latent Sunder Charms: two paths** (separate columns in Tab 1 when you search a Sunder unique; the six uniques are the `PreCrafted ...` rows of `uniqueitems.txt`). Sunder type weights equal the `Sunder Charms` TC weights 30/30/20/12/6/3.
  * **(a) Table path** - the `Sunder Charms` TC (Picks 1, ladder season 2/2). RotW: reached only through the `Herald Item` TCs (the desecrated champion/unique/super/boss TCs no longer include it, so there the table path is herald-only). LoD: included by every Hell desecrated champion/unique/super/boss TC (LoD has no heralds). Pure data; scales with players where the enclosing TC has NoDrop.
  * **(b) MF path** - the PreCrafted Sunders are also `spawnable=1` unique grand charms (`cm3`, lvl 75, rarity 1, `DropConditionCalc` `cond('Difficulty', hell)`), so a unique grand charm roll in Hell at ilvl >= 75 can pick one (weighted by rarity: 1 each against 15 for Gheed's Fortune and the other unique grand charms). This replaces the earlier hard-coded rule (`sunderMf*` constants, from the 3.2/3.3 patch notes); the tables now state it themselves.
* **Herald quality**: 3.2 "slightly reduced the chance for Heralds to drop Unique, Set, and Rare"; 3.3 "increased the chance of dropping Rare quality and higher from Herald Tiers 3+". Sizes unknown, so `CONFIG.heraldQualityAdj` = `{t12: {unique, set, rare}, t3plus: {rarePlus}}` defaults to 1 (no-op) and applies to herald rows only. The UI marks the herald quality columns as unadjusted.
* Not modelled: when a herald spawns (zone completion logistic), so there is no per-run herald odds; the "something desirable" fallback.

Sources: https://diablo2.io/post4136083.html (datamine thread), https://www.icy-veins.com/d2/reign-of-the-warlock-endgame-changes-for-diablo-ii-resurrected, https://news.blizzard.com/en-us/article/24266710/diablo-ii-resurrected-ptr-3-2-now-live, and the data guide pages `desecratedzones` and `monstats` (`TreasureClassHerald`).

## Items named explicitly in treasure classes

`spawnable=0` items and uniques are dropped only when a TC names them. The engine treats any item code or unique/set id named in a TC as a leaf (`dist`), and the Tab 1 search index lists every such item (`searchIndex`: `explicitI` for items, `explicitU` for uniques). Per-kill chances come straight from the TC walk, including the drop cap:

* **Colossal Ancient statue pieces** `ua1`-`ua5` ("Uber Ancient Summon Material Act N", `spawnable=0`): named by the `Ancient Statue 1-5` TCs (e.g. `Ancient Statue 1` = ua1 18, ua2 1, ua3 1), which the Hell act boss TCs and their Desecrated variants reference (`Andarielq (H)` has `Ancient Statue 1` at Prob 2).
* **Worldstone Shards** `xa1`-`xa5` (`spawnable=1`, level 75, rarity 14): from the `Act N Worldstone Shard Parent [Citem|Uitem] A`, `Act N (H) Herald Item Shard` and `Act N Terrorize Act Consumable` TCs reached from champion, unique, super unique and herald TCs. The "Act N" in these names is **not** the monster's act: `Act N Terrorize Act Consumable` is a pick of `xa1`-`xa5` biased towards `xaN` (weight 5 for the own shard, 1-3 for the others), i.e. N is the shard type. The monster act to shard parent mapping in the Hell TCs is a permutation (`Act 1 (H) Citem A` -> `Act 3 ... Parent`, 2 -> 4, 3 -> 5, 4 -> 2, 5 -> 1); the engine just follows the tables.
* **Keys** `pk1`/`pk2`/`pk3` (Terror, Hate, Destruction): `Countess Item (H)` / `Summoner (H)` / `Nihlathak (H)` and their Desecrated variants.
* **Uber Ancients**: the Hell-only monsters `colossal1-3` ("Ancient Barbarian 1-3", boss, `Level(H)` 110, Colossal Summit, level 137) have `TreasureClass(H)` = `Uber Talic` / `Uber Madawc` / `Uber Korlic` (group 40, level 110, Picks 1, NoDrop 0): one of two `spawnable=0` uniques each (Defender's Bile/Fire, Guardian's Light/Thunder, Protector's Stone/Frost), 50% per kill each before the cap. They are in `BOSS_AREA` and have no Normal/Nightmare row. The older `ancientbarb1-3` rows have no TC and stay skipped.

## Names and stat descriptions (string tables)

`build.py` loads `excel/strings/*.json` (enUS only; one shared map for both game modes, keys compared case-insensitively like the game does, first row wins) and resolves every display name from them. The table keys stay the ids; the display name is the `n` field (`name` for areas, `dn` for affixes, `sn` = set name on set items). Tab 1 search matches the display name, the old table key and the item code (`thudergod` and `thundergod` both find Thundergod's Vigor).

| Thing | Id kept | Display name from |
|---|---|---|
| base items | code | `namestr` -> item-names.json (falls back to the table `name` column: potions, gold, ...) |
| uniques, set items, sets | `index` | item-names.json (fixes table typos such as `Thudergod's Vigor`, `Que-Hegan's Wisdon`; shows renames such as `Mindrend` -> Skull Splitter) |
| magic prefix/suffix, automagic | `Name` (`n`) | item-nameaffixes.json (`TaintedAffix` -> Tainted) |
| monsters | `Id` | monstats `NameStr` -> monsters.json |
| super uniques | `Superunique` | superuniques `Name` -> monsters.json (`Siege Boss` -> Shenk the Overseer) |
| areas | level `Id` | levels.txt `LevelName` -> levels.json (`ColossalSummit` -> Colossal Summit, `Rigid Highlands` -> Frigid Highlands) |

The hard-coded `BOSS_NAMES` list is gone: act bosses use their monstats names. `colossal1-3` (the Hell Uber Ancients) are named by the strings `Talic`, `Madawc`, `Korlic` (the same strings as `ancientbarb1-3`, they do not carry an "Uber" prefix; their treasure classes are still `Uber Talic/Madawc/Korlic`). The Colossal statue pieces `ua1`-`ua5` are named Talic's Anguish, Korlic's Pain, Madawc's Ire, Bul-Kathos' Nightmare and Worusk's End (no word "statue" in the strings).

**Stat descriptions** follow the game's pipeline instead of the old `*Tooltip` column: `properties.txt` (property code -> `stat1..7`/`func1..7`) -> `itemstatcost.txt` (`descfunc`, `descval`, `descstrpos`, `descstr2`, `dgrp*`) -> string keys in item-modifiers.json. Values are written as `#` (`%d` -> `#`, `%+d` -> `+#`), so a description is both the label and the stat key used by the Tab 3 item builder (`+#% Faster Cast Rate`); each mod keeps its `min`/`max` and `Engine.describe(key, min, max)` turns them into `+10-20% Faster Cast Rate`.

* **descfunc 19** (plain sprintf, the bulk of the stats) and the other funcs whose D2R strings already contain their format: the string is used as is.
* **13** class skills (`charstats` `StrAllSkills`), **14** skill tabs (`charstats` `StrSkillTab1-3` + `StrClassOnly`; tab id = class index * 3 + tab - 1 over the charstats rows without the blank `Expansion` separator, so tabs 21-23 are Warlock Demon/Eldritch/Chaos), **15** skill on hit/attack/struck/death/kill/level-up, **16** aura, **24** charged skill, **27/28** single skill (skill names: skills.txt `skilldesc` -> skilldesc.txt `str name` -> skills.json), **11** repair, **12**, **5/10** (value*100/128: the Hit Causes Monster to Flee affix is exported as 25, not the raw 32), **17** per-level / time-of-day stats (`descstr2` "(Based on Character Level)"), and the classic funcs 1-4, 6-9, 18, 20-22 (value text before/after the string by `descval`) are implemented.
* Grouped stats (`dgrp`): a property whose stats all share a group is shown with the group string (`res-all` -> `All Resistances +#`, `all-stats` -> `+# to all Attributes`).
* The game combines damage ranges in code, not in the tables, so `RANGE` in `build.py` maps `firemindam`... to the `strMod*DamageRange` strings (`Adds #-# fire damage`, `Adds #-# poison damage over # seconds`), and `dmg%` (properties func 7, no stat) to `strModEnhancedDamage`.
* **Labels with several numbers** (about 130 rows: poison `Adds #-# poison damage over # seconds`, `Adds #-# <element> damage`, `#% Chance to cast level # <Skill> on striking / on attack / when struck`, `Level # <Skill> (#/# Charges)`): the label stays the stat key, and a data mod carries a sixth element `slots`, one `[lowest, highest]` per `#` in text order, which `Engine.describe(key, min, max, slots)` fills (row: the row's numbers, "all tiers": the ranges over the rows). `min` / `max` of such a mod are the number the builder slider filters on. Meaning of the numbers (properties.txt func, `ITEMMODS_PropertyFunc11/15/16/17/19` in D2MOO `D2Common/src/Items/ItemMods.cpp`):
  * **dmg-fire / ltng / mag / cold, dmg-pois** (func 15 + 16 [+ 17]): min and max damage are two fixed values of the row, they are not rolled (func 15 / 16 pass `nMin` / `nMax` as they are; every shipped row has min = max for poison). Slider = the maximum damage. The text is the range string (`Adds 1-2 fire damage`) and, when min and max are the same number, the game's single string (`+1 cold damage`, strModColdDamage; `+175 poison damage over 6 seconds`, strModPoisonDamage). Cold length (`param`) is not in the tooltip.
  * **Poison** is stored per frame in 1/256ths and `param` is the length in frames (25 per second): the tooltip total is `value * frames / 256` (C integer division) over `frames / 25` seconds, e.g. Pestilent small charm 299 x 150 -> `+175 poison damage over 6 seconds`. `build.py` converts at build time, so the slider and the conditions work on the total damage shown in the game (Foul (Envenomed) 128 and of Anthrax 86 are both 50).
  * **Chance to cast** (func 11): `param` = skill, `min` = chance % (0 or less -> 5), `max` = skill level (> 0 fixed; < 0 `(ilvl - reqlevel) / ((99 - reqlevel) / -max)`; 0 `(ilvl - reqlevel) / 4 + 1` capped at the skill max level, 20 if none; at least 1). Nothing is rolled. Slider = the chance (a percentage like the other stats, and the only number that separates the Teleport Shield tiers); the level is shown.
  * **Charged** (func 19): `param` = skill, `max` = skill level (same rules as above), `min` = max charges (0 -> 5; < 0 `level * -min / 8 - min`; clamped to 1..255, as in the decompilation). The item drops with `max / 8 + 1 .. max` charges left (random), hence `(5-67/33-67 Charges)`. Slider = the skill level, **at item level 99** (lower item levels roll lower levels; the builder's odds do not model that, they use the level at item level 99).
  * **Poison from several sources** (LoD 1.10-1.14 decompilation, `D2Game/src/UNIT/SUnitDmg.cpp`): every poison property adds its per-frame damage, but `ITEMMODS_AddPropertyToItemStatList` / `ITEMMODS_PropertyFunc15` count each poison source in `poison_count` and the hit divides the summed length by it (`dwPoisLen /= nPoisonCount`). The item tooltip shows the summed length, so a Pestilent + of Anthrax small charm reads `+451 poison damage over 12 seconds` (385 x 300 / 256), but as the only poison source deals about 225 over 6 seconds (385 x 150 / 256).
* **Tooltip fallback** (property tooltip, or a fixed text for `coldlength`/`poisonlength`): `sock` (no description row for `item_numsockets`), `cold-len`, `pois-len`, `dur`, `fade`, `state`, `bloody` (no `descfunc`), `ethereal`, `reanimate` (descfunc 23, needs a monster name), `red-dmg%` (descfunc 29). `build.py` prints the list per mode; none of them is a skill tab, class skill or normal stat.

## Assumptions and limitations

* Super unique and boss locations are not in the tables; `SU_AREA`/`BOSS_AREA` in `build.py` are hand-written, with `SU_AREA` cross-checked against the Arreat Summit act 1-5 super unique pages and PureDiablo's superunique overview (source noted per changed row). Their mlvl depends on that area. Rows that exist in `superuniques.txt` but never spawn (Winged Death, The Tormentor, Taintbreeder, Riftwraith the Cannibal, Axe Dweller, Anodized Elite, Vinvear Molech, Magma Torquer, Blaze Ripper, Flamespike the Crawler) are listed in `SU_UNUSED` and are not sources. Baal's five minion waves (`Baal Subject 1-5`) are mapped to the Throne of Destruction. Ancient Kaa is placed in Tal Rasha's Tomb (66); Stormtree in Lower Kurast (79). The quest Ancients (`ancientbarb1-3`, Talic/Madawc/Korlic of the Arreat Summit fight) have no drop TC in the tables (every `TreasureClass*` column in `monstats.txt` and `TC*` column in `superuniques.txt` is empty) and are skipped; the Uber Ancients are separate monsters (`colossal1-3`, see above) and are included. `uniqueitems.txt`'s new `disableChronicle` column and the Crafted (non-PreCrafted) Sunder rows are not used.
* **Boss quest drops** ("Show boss quest drops" checkbox next to Difficulty / Act, setting `quest`, off by default): each act boss with a `TreasureClassQuest` / `(N)` / `(H)` TC gets a second row, "<Boss> (quest)", on that TC next to its regular row. The quest kill is the first kill only, so the row has no kills per run ("first kill") and adds nothing to area totals; Andariel gets no extra row because her regular TC already is `Andarielq`. In the game (D2MOO `D2Game/src/MONSTER/MonsterMode.cpp`, after the normal/champ/unique TC is picked) the quest TC replaces it when monstats `TCQuestId` is set, `TreasureClassQuest` is non-empty, and the killing player (or a minion's owner) has not completed that quest, has no reward pending, and has not reached checkpoint `TCQuestCP`. So it applies to the first kill while the quest is open (Mephisto/Diablo/Baal checkpoint 0, Duriel 5, Andariel 1). Monsters with it in this data: Andariel, Duriel, Mephisto, Diablo, Baal. Quest TCs drop no gold/junk and have Rare=1024 (rare-or-better) and Unique/Set 993. Andariel's normal `TreasureClass` already is `Andarielq` in every difficulty, so the toggle changes nothing for her (D2R always uses it). Bosses keep their own TC (no group upgrade) unless terrorized, also for quest TCs. **ASSUMPTION** (`CONFIG.questOverridesTz = true`): D2MOO's quest check runs last and overrides whatever TC was chosen, but D2MOO is 1.10 (no desecrated TCs), so D2R's behaviour in a terror zone is unknown; the quest TC is assumed to override the desecrated TC too. Andariel's desecrated columns are `Andarielq ... Desecrated`, hinting that the desecrated column may be used as-is in TZ; set the flag to `false` for that.
* Unique minions use the normal TC at mlvl+3; Reign of the Warlock extras (herald minions/unique mod counts, always-unique mods) and the +25% terror zone XP are ignored. The terror zone bounds come from the `rotw` or `expansion` section of `desecratedzones.json` depending on the data file (identical numbers today).
* `QuestFlag`, `ConditionCalc`, `DropConditionCalc` ignored; ladder season gating follows `CONFIG.currentSeason` (see Treasure classes).
* Names come from the game's English string tables (see below); table keys stay the ids (URLs, tests). Where a string is missing the table value is shown (for example `Nihlathak` has no monsters.json row, potions use the `name` column).
* Rare odds are exact (no sampling noise, also for very small probabilities). Magic is exact (including the staff mod skills). The same affix cannot be satisfied by summing two affixes, and "chance to cast" style stats are matched on label only.
* Per-run counts are a rough model (see above), and ignore waypoints/route length, wandering monsters, shrines, and that a real clear never kills everything.
